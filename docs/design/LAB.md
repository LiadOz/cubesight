# Design lab workflow

Open `#/dev/lab` from the developer drawer (press the backtick key) while running the Vite dev server. Each proposal also has a deep link such as `#/dev/lab/history-list`. The page is excluded from the production route table. Its previews load the real app route in same-origin iframes, replace local storage with per-frame memory storage, disable IndexedDB, and seed only the selected fixture. The results fixture uses the real Brain controller and the shared smart-cube session with a scripted replay adapter; History uses valid stored-record fixtures migrated into its in-memory fallback.

Add a proposal as `src/dev/lab/proposals/<id>.js`, then register it in `src/dev/lab/registry.js`. Export `{ id, title, why, page, route, component, fixture, states, variants }`; each variant has `{ id, label, description, apply() }`. Keep every variant behind selectors scoped to the proposal and variant. Use actual app routes and shared components, never screenshots or duplicated page markup. Add fixtures through the preview bootstrap or real test drivers, not hand-built view models that pretend to be app state.

The lab shows one, two, or three variants side by side when the available width allows it. Use the viewport and Orbit theme selectors to compare responsive states. Press `1`, `2`, or `3` to reload the matching preview. Feedback is stored locally and exported as JSON; the Vite-only `/__lab-feedback` endpoint also writes each pick, rejection, or note under `/tmp/cubesight-lab/`.

Do not promote a proposal automatically. After the user picks a variant, record the decision in `docs/design/lab-decisions.md`, promote that exact variant in the owning product component, and remove the losing variants. Check `docs/design/WIDGETS.md` first: only registry items marked approved can change production UI. F8 and F9 suites should ignore lab routes except for a smoke check that `#/dev/lab` is available in development and absent from production.
