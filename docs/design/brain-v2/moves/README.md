# Move & algorithm guide — how to show HOW to perform a move

Notation alone ("R U R' U'") does not tell the user which way to turn, which
face is meant when the cube is held unusually, or whether `y` means "turn a
layer" or "turn the whole cube". This folder explores one reusable guide that
can sit anywhere the app gives the user a sequence: guided scrambles,
wrong-turn recovery, algorithm trainers (OLL/PLL), coach "best move was
F' R D2", solve review, drills.

Open `../index.html` (new group "Move & algorithm guide") or the PNGs here.
Everything is generated by `_src/genMoves.mjs` (see "Regenerating" below).

The five shared examples (all generated from the same move/cube model, so the
cube states are real, not hand-drawn):

1. guided scramble step, current move `R'` (move 15 of the standard scramble)
2. T-perm `R U R' U' R' F R2 U' R' U' R U R' F'`, current move `R2` (held yellow-top, green-front)
3. rotation: `y'` then `R U R'`
4. wide: `r U R' U' r' F R F'`, current move `r`
5. slice: `M' U M`, current move `M'`

## How each kind of move is drawn (shared by all approaches)

| kind | visual rule |
|---|---|
| face turn | the turning layer stays at full colour, everything else is dimmed; a curved arrow sits on the outer face of that layer |
| prime | same layer, arrow sweeps the other way (and the label carries the `'`) |
| double | the arc is longer and has **two** arrowheads; a half turn has no direction, so either way is fine |
| wide (`Rw`, `r`) | two layers lit; one arrow on the outer face |
| slice (`M E S`) | one middle layer lit; **no ring**, only straight flow arrows on the two visible belt faces (a ring around an invisible axis would be misleading) |
| rotation (`x y z`) | nothing is dimmed; a **dashed** ring around the whole cube, dashed chip border, label "rotate cube" |
| hidden face (`L B D`) | the camera swings to the opposite corner (below-left-back) so the turning face is visible and the arrow is still clockwise as seen from outside; a small note says so |
| mistake / recovery | the same chip / arrow in `--b-warn`, with a cross on the chip that was wrong; the plan chips stay where they are (see `M-08`) |

Colour roles follow `../tokens.md`: accent = the plan, ink = arrows, warn =
correction, faint = done. Stickers use the `--b-st-*` palettes.

## The four approaches

### A — arrows on a 2D isometric cube (`M-03`)
A curved arrow on the turning face plus thin flow arrows on the two visible
side faces (they show which way the *neighbouring* stickers travel, which is
what beginners actually look at). Layer lit, rest dimmed. Rotations get a
dashed ring, slices get flow arrows only.
- **Pros:** static, so it works in print-like places (review, history, coach
  text, tooltips); no runtime 3D; deterministic; cheap to render in SVG;
  shows the cube colours so the user can match the face.
- **Cons:** one move at a time; needs a camera swing for `L B D`; the arrow
  is a symbol the user must read (no sense of motion).

### B — live 3D ghost on the real cube (`M-04`)
On the three.js cube the user already sees (and which follows the gyro), the
target layer lifts about 0.3 cubie and plays the turn in a loop (about 0.9 s,
ease in/out), with a dashed outline where it lands. An arrow overlay is
optional. Because it runs on the real cube, it is automatically correct for
however the cube is held: the guide picks the *physical* face and the layer
turns wherever that face is on screen. The static frames show the mid-turn
pose plus "now" and "after".
- **Pros:** the most unmistakable (you see the motion); always matches what the
  user sees; no camera swing needed, because the user can turn the cube.
- **Cons:** needs three.js work (see "3D cube hooks"); not usable where there
  is no live cube (review lists, text); slices and rotations need new animation
  paths; must fall back for reduced motion; hard to show a whole sequence.

### C — move chips strip (`M-05`)
A strip with one chip per move: a small schematic cube (turning layer lit, one
arrow) and the notation under it. The current chip is enlarged (glyph, big
notation, "counter-cw" / "half turn" / "rotate cube" / "middle layer" caption).
Done chips fade; triggers are bracketed ("sexy move"); fingertricks appear for
the current move only. Scrambles show a window around the current move.
- **Pros:** the only approach that shows the *whole sequence* and its rhythm;
  grouping teaches algorithms as chunks; works at phone width (scrolls); one
  component for every host; text and glyph are both available.
- **Cons:** small glyphs are schematic, not the real colours; the arrow on an
  18 px glyph is easy to misread on its own, so it should not be the only cue
  for the current move (hence the enlarged chip and the pairing with A or B).

### D — unfolded net and top-down (OLL) view (`M-06`)
Six faces laid out as a cross; every face is seen from **outside**, so a
clockwise arrow on a face is clockwise on screen. Flow arrows on the four side
faces; one curved arrow on the turning face (both R and L faces for `x`). For
last-layer algorithms a top-down view with the four side strips, the standard
OLL diagram.
- **Pros:** shows all six faces at once, so there is no hidden-face problem;
  the top-down view is what cubers already use for case recognition, so it
  doubles as the algorithm-picker card; no 3D.
- **Cons:** the eye has to map a flat cross to a real cube; busiest to read;
  a `D` or `E` turn is not visible in the top-down view ("not visible from
  above" note); large.

## Recommendation

Combine, with one component and one move model:

1. **C everywhere** as the sequence spine (scramble, recovery, algorithm,
   coach, review). It is the thing that is always on screen and the only
   approach that shows more than one move.
2. **B on the main 3D cube** wherever a live cube is on screen (guided
   scramble, inspection hints, algorithm trainer, drills). On by default
   for a guided step; `g` toggles it; it loops until the user turns.
3. **A for static contexts**: solve review, coach lines, history tooltips,
   the vocabulary in help, print/share. It is also the fallback whenever
   the 3D ghost is unavailable (reduced motion, no WebGL, slice or rotation
   before the 3D hooks exist).
4. **D only as the algorithm-picker card and for last-layer cases**
   (top-down view). Not as a guide while turning; it is too indirect.

`M-07`, `M-09` and `M-10` show the combination: B on the cube inside the Orbit
ring (ring segments = moves, group gaps for triggers), the big notation and
the words on the right, C along the bottom. Mono keeps the same content but
puts the moves on a monkeytype-style word stream on top and drops the ring.

Reasons: the approaches fail in different places (C has weak glyphs, A is
static, B needs a live cube, D is indirect), and the pairings cover each
other's weak spot.

## Component API proposal

One factory and a few pure helpers, in the style of `createSmartCubeTurnGuide`
(which this replaces; its prev/next buttons, live region and recovery wording
carry over).

```js
// src/move-guide.js (proposal; not written yet)
const guide = createMoveGuide(host, {
  moves: ['R', 'U', "R'", "U'", /* ... */],  // WCA notation: R Rw r M x, with ' and 2
  index: 0,                                  // current move; moves.length = finished
  held: { bottom: 'D', front: 'F' },         // from the gyro (cube3d.getHeldFaces())
  frame: 'held',                             // 'held' | 'start'  (see "Frames of reference")
  variant: 'auto',                           // 'auto' | 'chips' | 'arrows' | 'ghost' | 'net'
  parts: { chips: true, cube: 'auto', words: true, fingertricks: 'current' },
  grouping: 'auto',                          // 'none' | 'auto' | [[0,3,'sexy move'],[4,9,''],...]
  statuses: { 2: 'wrong' },                  // per-index: 'wrong' | 'fix' | 'best' | 'played'
  window: [5, 6],                            // chips before/after the current one (null = all)
  cube3d,                                    // optional handle for the ghost (see below)
  state,                                     // optional cube state, to draw real colours in A/D
  onStep(delta) {}, onSelect(index) {},      // prev/next, clicking a chip
});
guide.update({ index: 3, held, statuses });  // cheap, no re-layout of untouched chips
guide.describe(3);                           // { notation, kind, symbol, text, physicalFace, colour, layers, angle }
guide.destroy();
```

`variant` picks what draws the current move: `'chips'` = strip only;
`'arrows'` = A on an SVG cube; `'ghost'` = B on `cube3d`; `'net'` = D.
`'auto'` = ghost if `cube3d` is given and motion is allowed, else arrows; the
chip strip is shown in every case unless `parts.chips` is false. A host that
only needs the picture in a list (review) calls the pure renderer directly:

```js
import { renderMoveGlyph, renderMoveArrows, renderNet } from './move-guide-render.js';
renderMoveArrows(svgHost, { move: "R'", held, state, size: 44 });   // variant A as a string/SVG
```

Pure helpers to export next to it (all unit-testable, no DOM):

```js
parseMove("Rw'")          // { kind:'wide', letter:'R', axis:'x', layers:[0,1], double:false, prime:true, angle:+90 }
describeMove(move, held, state?)    // extends describeTurn: adds x y z, M E S, r/Rw; symbol + text + colour
expandToHeld(moves, startHeld)      // for frame:'start': each move with the held frame it is written in
heldAfter(held, move)               // held frame after a rotation (x y z) or unchanged
groupMoves(moves)                   // known triggers (sexy, sledge, sune...) + explicit groups
fingertrick(move, { hand:'right' }) // text hint, or null
```

The pure geometry in `_src/geom.mjs` (layers, signs, camera, arrow paths) is
what the mockups use; it can be lifted into `move-guide-render.js` more or
less as is.

### How the rest of the app reuses it

| host | call |
|---|---|
| guided scramble | `moves` = scramble in held notation (as `movesForInspection` already produces), `index` = progress, `variant:'auto'`, `window:[5,6]`, no grouping |
| wrong-turn recovery | same strip, plan chips unchanged; insert the recovery turns as `'fix'` chips after the `'wrong'` chip (`recoveryMoves` gives them); arrows and ring in warn colour; `describe()` text replaces the current "Return to plan" line |
| algorithm trainer (OLL/PLL) | `moves` = the algorithm, `frame:'start'`, `held` = the trainer's hold, `grouping:'auto'`, fingertricks on; the case card is the D top-down view; drill mode: `parts.chips:false` after N clean runs, ghost on demand |
| coach "best move F' R D2" | `statuses` `'best'` on the three chips, arrows (A) on hover/click, ghost when the live cube is on screen |
| solve review | `renderMoveGlyph` chips per recorded move, `'played'` vs a suggested line; clicking a chip moves the replay cube (`onSelect`) and the ghost follows |
| help / vocabulary | `M-01` is this component's own `renderMoveArrows` over 12 moves |

### Frames of reference (important for algorithms)

The letters in a sequence only mean something relative to how the cube is
held. There are two cases:

- `frame:'held'` (scramble, recovery, plan): the moves are already written for
  the orientation in `held`, exactly like today (`movesForInspection` /
  `displayMoves`). `held` is refreshed from the gyro.
- `frame:'start'` (algorithms): the moves are written for the orientation in
  `held` at index 0; `y'` in the middle changes the frame for everything after
  it (`heldAfter`). The guide draws each step in its own frame. If the gyro
  disagrees with the expected frame, show a one-line hint ("hold green in
  front") rather than silently drawing the wrong layer.

### 3D cube hooks (for the ghost; to be built later)

`src/cube-3d.js` already has the important pieces: `animateMove` turns a
layer about the outward normal of the face by `-direction * turns * 90°`
(R = -90° about +x, which is clockwise seen from the right), wide moves take
the two layers, reduced motion is honoured, and `getHeldFaces()` reads
bottom/front from the group quaternion. What the ghost needs on top:

- `previewMove(spec, { loop, lift, opacity })` and `clearPreview()`: same layer
  grouping as `animateMove`, but looping, with a 0.3 cubie lift and a
  translucent copy; `spec` = `{ axis, layers, angle }` from `parseMove`, mapped
  from the held letter to the **physical** face the same way `describeTurn`
  does (see next section).
- Slices (`M E S`), rotations (`x y z`) and lowercase wide (`r`): `animateMove`
  ignores them today (`FACE_NORMALS[face]` is undefined), so the ghost needs
  the `layers`/`axis` form above rather than a face letter.
- A `held` change (gyro) must not restart the loop; only a change of move or
  index does.

## Orientation mapping rules

Read from `src/smart-cube-guidance.js`, `src/cross-cube.js`, `src/cube-3d.js`.

1. **`held = { bottom, front }`** are *physical* faces (`U D F B R L`, the
   colour frame of the cube: white top, green front when solved), as reported
   by `getHeldFaces()`.
2. **`inspectionOrientation(bottom, front)`** gives `top = opposite(bottom)`
   and `right = top × front` (cross product of the face normals). Checked by
   hand: the default hold (D, F) gives top U (white), right R (red); hold
   (U, F) gives top D (yellow), right L (orange); hold (D, R) gives front R
   (red), right B (blue). `M-02` draws exactly these.
3. **The letters of a move name the face by where it is now**, not by colour:
   `U` = the face on top, `D` bottom, `F` front, `B` back, `R` right, `L` left
   as the user holds the cube. `movesForInspection` / `displayMoves` translate
   canonical (colour-frame) moves into those letters.
4. **`describeTurn(move, bottom, front)`** maps the letter back to the physical
   face (`{U: top, D: bottom, F: front, B: opposite(front), R: right, L:
   opposite(right)}`), then names it by **the colour of that face's centre**
   (`FACE_COLORS`), and says clockwise / counterclockwise / 180° "looking
   directly at that face". A quarter turn is clockwise as seen from outside
   that face; `'` reverses it; `2` is a half turn. Wide (`Rw`) says "two
   layers". The symbol is `↻ ↺ ½`.
5. **Slices** follow a reference face (WCA): `M` like `L`, `E` like `D`, `S`
   like `F` (`SLICE_REFERENCE`). When a detour is re-expressed for another
   hold, `displayMoves` picks the slice on the new axis and flips it when the
   reference face is opposite (`SLICE_FOR_FACE`: e.g. physical `M` on a cube
   whose `L` is now at the user's right becomes `M'`).
6. **Rotations** follow a face: `x` like `R`, `y` like `U`, `z` like `F`.
   After one, the held orientation changes; the guide draws and names later
   moves in the new frame (`M-02`, rule 3). Not handled by `describeTurn`
   today (see below).
7. **Hidden faces** (`L B D`): draw from the opposite corner (below-left-back).
   The arrow is still clockwise **as seen from outside that face**; that is
   what notation means, and it is what the user sees when they look at the
   face. The 3D ghost does not need this, because the user can turn the cube.

Gaps found in the existing code (for the builders, not fixed here):

- `describeTurn` returns `null` for `M E S x y z` and lowercase `r` (its
  `FACE_POSITION` only has `URFDLB`), so the turn guide would show the bare
  notation with no text for them.
- `parseScramble(..., { allowWide: true })` accepts `Rw` and `M E S`, but not
  lowercase `r` or rotations, which algorithm notation uses.
- `animateMove` does not animate slices or rotations (see above).

## Accessibility

- **Every move has a text alternative**, from `describe()`: e.g. "Move 7 of
  14: R2. Turn the right face (orange center) 180°, looking directly at that
  face." For rotations "Rotate the whole cube the opposite way to the top
  face", for slices "Turn only the middle layer (left-to-right) the opposite
  way to the left face (orange center)". Glyphs are `aria-hidden`; the chip
  is a `button` (or `li` with `aria-current="step"`) whose accessible name is
  that sentence.
- **Announcements:** the host keeps `aria-live="polite"` as the current turn
  guide does, and announces only the current move (and "Return to plan: L2"
  on a wrong turn), not the whole strip. A summary for the list:
  "T-perm, 14 moves in 3 groups."
- **Nothing relies on colour alone:** prime = arrow direction + the `'` in the
  label + the word "counterclockwise"; double = two heads + `2` + "half
  turn"; rotation = dashed + "rotate cube"; wrong turn = cross + the words
  "played" / "undo". Contrast follows `../tokens.md` (ink and accent on
  surface pass AA; warn text uses `--b-warn-text`).
- **Keyboard:** roving tabindex through chips, `←` `→` step, `space` next,
  `g` toggles the ghost, `f` toggles fingertricks. Touch targets: chips are at
  least 58 x 82 px.
- **Reduced motion** (`prefers-reduced-motion: reduce`): no looping ghost, no
  chip "grow" transition, no scroll animation. `variant:'auto'` falls back to
  A, or to the ghost frozen at mid-turn with the arrow on. `animateMove`
  already sets its duration to 0 here, which would show only the end state, so
  the preview must not reuse that path blindly.

## Fingertricks

The hints in the mockups (`FINGER` in `_src/draw.mjs`) are **placeholder
data**: plausible right-handed CFOP defaults (R wrist push, R' ring-finger
pull, U right-index flick, U' left-index flick...), not reviewed by a cuber.
They are shown only for the current move and can be turned off. They need a
proper table, per hand, before shipping; see open questions.

## How the arrow directions were checked

The arrows are not drawn by hand. All approaches come from one geometry model
(`_src/geom.mjs`) in which a face turn is a right-handed rotation about the
face's outward axis by -90° (R about +x, U about +y, F about +z; L, D, B are
+90°), the standard "clockwise seen from outside". `_src/selftest.mjs`
(`node _src/selftest.mjs`) checks it independently of the drawings:

- **Sticker flow:** after one turn, the named piece lands where notation says:
  R sends FR to UR and UR to BR; U sends UF to UL; F sends UF to FR; L sends FL
  to DL; D sends DF to DR; B sends UB to BL; `M` moves the front centre down
  (like L), `E` right (like D), `S` moves the top centre right (like F); `x`
  front to up, `y` front to left, `z` top to right; `R'` the reverse.
- **Group laws:** every move followed by its inverse, four quarters, and two
  halves all return a solved cube (16 move kinds); `r = R M'`, `x = R M' L'`,
  `Uw = U E'`.
- **Real algorithms:** the T-perm leaves the bottom two layers solved, is its
  own inverse, swaps exactly UFR/UBR corners and UL/UR edges (a mirrored or
  reversed turn would break this); the `r U R' U' r' F R F'` OLL leaves the D
  layer intact.
- **Screen sense:** from the camera chosen for each face, the projected arc of
  R U F L B D is clockwise on screen and of the primes anticlockwise
  (signed-area test); belt arrows follow the flow (R up on the F face, U left
  on the F face, F right on the U face). The net and top-down views use the
  same functions with each face seen from outside.
- **Held orientation:** default hold gives white/green/red, hold (D, R) gives
  red front and blue right.

Then every PNG was read at full size: overlaps and clipped text (the render
step also runs a text-overlap / out-of-canvas check), the chip glyph
overlapping its label, net face labels colliding with neighbouring faces,
captions running past their cells, chips spilling across panels and a bracket
cut off at the bottom were found and fixed. Known cosmetic limit: the B frames
are painter-sorted SVG, so the slice mid-turn pose is shown at a small angle
(about 12°); the real three.js cube has no such artefact.

## Open questions

1. **Fingertricks:** which set (standard CFOP? the user's own?), for which
   hands, and who reviews the table? Left-handed and mirrored modes?
2. **Double turns:** direction is free in the picture. Should the guide prefer
   the direction that matches the next move (R2 before U' = anticlockwise)?
3. **Rotations on a smart cube:** only the gyro sees `x y z`. Is it acceptable
   to treat a rotation step as "done" when `held` changes to the expected
   frame, and what happens when the user never rotates but turns other faces?
4. **Wide moves and slices from the cube:** smart cubes report face turns. Does
   the session model see `r` as `R M'` (two events) and can the guide confirm
   it, or is wide/slice guidance display-only?
5. **Default variant per host:** ghost on by default everywhere it can be, or
   only after the user asks ("show me")? Phone: chips + arrows (A) only?
6. **Grouping source:** a small library of named triggers, per-algorithm data
   in the trainer, or auto-detect only?
7. **Mirror/left-hand hold:** should `held` ever mirror the notation (a
   left-handed user holds R on the left)? Assumed no.
8. **Chip glyph in Orbit light / Mono light:** the glyph uses the dark cube
   body, which is heavy on paper backgrounds; a lighter outline-only glyph for
   the light modes is worth a second look.
9. **No phone or motion frames** were made here; the strip scrolls and the
   enlarged chip should stay pinned at the left edge on phones.
