Same ground rules as SPEC-NEXT / REVIEW-NEXT. **Direction change:** Orbit (dark first) is the primary experience. Keep Mono/light working, but don't spend effort polishing them, and never let them block an Orbit improvement. Layout/visual redesign items (a bigger cube, the scramble on the ring, the results/history redesign, fewer buttons, no duplicated splits) wait for the new designs in `docs/design/orbit-v3/` (in progress); don't start those until the designs land.

## Do now
1. **Smart cube in drills.** Drills should use the connected smart cube like solve does: connect from the drill (the same connect flow/chip as solve, sharing the one session), mirror physical moves on the drill's 3D cube in real time (gyro orientation too), and show the CORRECT state. The user saw a wrong/unclear state in drills. Reproduce first: open a drill with the fake cube harness, turn moves, and compare the drill cube with `session.getSnapshot().state`. Where a drill sets up a case (alg/OLL/PLL/F2L/cross/lookahead), the physical cube is generally NOT in that state, so make it explicit: either the virtual case (labelled "case") or the mirrored physical cube (labelled "your cube"), and use the guided setup (the guided-scramble engine) to bring the physical cube to the case when the drill needs it. Tests with the fake cube for mirroring + state equality.
2. **Examples animate FULL turns.** Alg playback, "better solution" replays, cross/lookahead plan playback and any demonstration animate complete quarter/half turns (smooth, readable speed). The partial "cue" stays only as the live hint for the next move the user must make in a guided scramble/recovery.
3. **Praise good play.** The coach/review must also call out what went well, not only mistakes: the optimal or near-optimal cross / X-cross, choosing the best available F2L pair (per the pair engine), an efficient pair (≤ the proven minimum + 1), a good pseudo pair, skips, a fast recognition, a clean LL. Positive markers on the ring, ranked alongside the negatives, in friendly cubing language (VOICE.md). Each must be evidence-based (proven/verified results only; no praise from partial searches unless labelled).

## Design-system principle (the user, 2026-10-01): one Cube + one Orbit
"The orbit is a cool design concept that I want consistent throughout… a very common component along with the cube itself. We have too many components that are different from each other. I want common components and a general UX flowing through all the flows."
- Consolidate to TWO core components with one API each: **Cube** (`src/cube-3d.js` + the page-cube wrapper: sizes, live/case/replay, highlight, cue, full-turn playback) and **Orbit** (one ring component: segments with state/weight/label/marker, a caret/center, an outer-label rule, a mini-glyph variant). Every flow maps its data onto these: the scramble, inspection, solving/results, alg playback, drill rounds, the timer, history/progress.
- Retire the one-offs once the Orbit covers them: the separate timer/inspection rings, the alg-page ring with split labels, duplicated split bars/tables, ad-hoc chip strips (keep a single chip component). Mono can keep its lane as a style skin of the same data, but Orbit is the reference.
- The exact visual spec comes from `docs/design/orbit-v3/` (in progress). The engineering consolidation (a component audit + migration plan) is the first task after a direction is chosen.
